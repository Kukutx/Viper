# HTTP dependency migration

Reviewed on 2026-10-01, from task baseline `8ac8fe057f49883efb3357b831b1cfc67ca60947`.
This change migrates the application's reqwest dependency from locked 0.12.28 to
0.13.5. It does not finish every HTTP/TLS, platform or native dependency upgrade.
The published version and breaking changes were checked against the upstream
[0.13.5 release](https://github.com/seanmonstar/reqwest/releases/tag/v0.13.5),
[manifest](https://github.com/seanmonstar/reqwest/blob/v0.13.5/Cargo.toml) and
[client implementation](https://github.com/seanmonstar/reqwest/blob/v0.13.5/src/async_impl/client.rs).

## Dependency and TLS decisions

The manifest still disables default features. Blocking and async clients, SOCKS,
JSON, gzip and zstd remain available. `query` is now explicit because recording
uploads use `RequestBuilder::query`; it was implicit in 0.12. `native-tls-no-alpn`
preserves the previously selected native TLS feature boundary. `rustls-no-provider`
uses the existing ring provider instead of silently adding the new aws-lc default.
No HTTP/3, system-proxy or unrelated feature is enabled to resolve the upgrade.

Reqwest 0.13's normal Rustls path uses platform-verifier roots. Viper already used
bundled webpki roots together with native roots on desktop and a maintained mobile
fallback verifier. Both HTTP factories now use the existing
`hbb_common::verifier::client_config` for Rustls on every platform, not only mobile.
This preserves that trust-source policy without cloning verifier code or modifying
the shared server submodule. The resolved Rustls 0.23.45 type is shared with reqwest;
the real preconfigured-backend test rejects an incompatible `ClientConfig` downcast.
Desktop Rustls also keeps the previous HTTP/1.1 ALPN offer explicitly; mobile
preconfigured TLS keeps its existing ALPN behavior. The modern `tls_backend_native`, `tls_backend_preconfigured` and
`tls_danger_accept_invalid_certs` names replace their deprecated aliases.

The targeted Cargo update changes only the reqwest package identity. The graph has
1123 identities rather than 1128: old reqwest and five unused optional dependencies
leave, and reqwest 0.13.5 enters. Those five are `quinn`, `quinn-proto`, `quinn-udp`,
`lru-slab` and `rand_pcg`; this is resolver pruning, not removal of an enabled
application transport. All other package identities, including all 59 Git package
identities and their exact commits, remain unchanged. Some shared package dependency
lists are normalized by Cargo. The hbb_common Gitlink, FRB pin and pub lock are unchanged.

The lockfile was generated by Cargo, not edited by hand. Preparation run
[36855780847](https://github.com/Kukutx/Viper/actions/runs/36855780847) checked Git
identities and stored immutable lock blob `cbc18a12a38a6179dfb28c26fa647fe33b40f047`.
Artifact `11158007832` has SHA-256
`958df28fb499e772acaced752d793c2bd1f5a3553ed2f11445ba6beb451836d5`.
The source snapshot, resolver log and both lockfiles were downloaded and compared.
Preparation jobs may store reviewed Git objects, but never move task refs or run
application code with a write token. They are removed from the validation branch's
latest tree before native validation and are not part of the task branch.

## Private network regression

On Linux x64, first prepare the same native environment as `flutter-validate.yml`,
then run:

```sh
bash tools/native/setup-linux.sh
source tools/.reports/native.env
bash tools/native/test-http.sh
```

The script compiles the named Cargo integration target with the existing locked
Flutter/native profile and explicit `http-contract-tests` feature. That empty
feature is not enabled by default; its `required-features` test target prevents an
ordinary workspace test from unexpectedly requiring private certificates/settings.
CI unconditionally invokes the wrapper, which enables the feature and runs the
complete native test binary. No test uses `#[ignore]` or an allowed-failure step.

Tests compile the production `src/hbbs_http/http_client.rs`, not a replacement
factory. Dedicated server threads listen only on random loopback ports. The wrapper
creates short-lived test certificates and a private HOME, poisons ambient proxy
variables, and sets trust overrides only for the test process. Cargo runs before
HOME is changed. The executable comes from Cargo's JSON output, never a guessed
binary from an older build. Socket/request timeouts and a process timeout bound the
run. Exit cleanup removes only the private fixture directory; no system CA store,
personal application settings or running desktop service is changed. Private keys
are outside `tools/.reports` and never uploaded.

The regressions exercise synchronous/asynchronous JSON and query encoding, binary
upload bytes, native/Rustls trust and hostname rejection, explicit invalid-certificate
opt-in, strict HTTPS factories with an unsafe cached probe, HTTP/HTTPS/SOCKS5 proxy
authentication, gzip/zstd decoding, redirect credential stripping, streaming length,
HTTP error propagation, preconfigured-backend acceptance, proxy TLS cache keys and
actual desktop HTTP/1.1 ALPN negotiation.
Full logs are `tools/.reports/http-contract-build.log` and
`tools/.reports/http-contract-tests.log`. The existing Flutter, authentication,
network-interface, private PulseAudio, real FFI and desktop bundle checks remain.

## Regression surface and limits

The only existing application implementation changed is the HTTP factory macro.
Its callers in account discovery, recording uploads, downloads, software updates
and shared HTTP helpers keep their signatures, request construction and response
handling. These paths necessarily consume the new dependency and need application
acceptance testing. The existing non-strict certificate fallback, proxy-construction
error fallback, redirect policy and TLS cache algorithms are not rewritten. The
strict-factory tests demonstrate their specific existing guard; they are not a
claim that all transport policies are fail-closed or a complete security audit.

Manifest/lock, the explicit private test target and the required Linux CI step are
build/test changes. No Rust/Dart bridge signatures or generated bindings, protocol,
application/signing identities, localization or system permission declarations change.
Native builds on other platforms establish compilation and bundle/FFI consistency,
not device-specific HTTP trust/proxy execution. Loopback HTTP tests do not substitute
for real account servers, the production updater, Android/iOS trust stores, GUI,
remote sessions or installer acceptance. Dependency graph review remains a separate
required repository setting; it is not disabled or replaced by these tests.

Exact candidate and task-head validation runs are recorded in PR #1. A successful
resolver or tool test is not an application build; a historical candidate success
does not certify a later task head. No signing, publication or production deployment
is performed by this migration.

## Fail-closed construction and strict HTTPS (2026-10-03)

All synchronous/asynchronous HTTP factories now return `ResultType<Client>`.
Proxy parsing/setup, shared TLS initialization and reqwest construction failures
return a typed `HttpClientConfigError`, never an unconfigured default client.
Errors deliberately omit proxy userinfo. Both generic API fallback dispatchers
propagate configuration errors without retrying the rendezvous TCP transport;
ordinary connection/5xx fallback and explicitly selected raw TCP mode retain
existing semantics. Account initialization propagates failure and does not mark
the API warmed. Recording upload initialization reports the error and stops its
upload worker without deleting local recording files. Update discovery, POST
and general requests propagate the same construction error.

Strict factories enforce HTTPS on the constructed client, not only its initial
URL: direct reuse for HTTP and HTTPS-to-HTTP redirects are rejected. Verified
HTTPS redirects still work. A cached `Plain` backend is not usable as strict TLS
evidence. Neither an insecure cached probe nor the insecure opt-in can lower
strict factory verification.

Scope correction to the earlier architectural review: the inherited
`allow-insecure-tls-fallback` setting must explicitly be `Y` before the nonstrict
factories may relax certificate verification. The shared configuration already
defaults that option to disabled. This change preserves the explicit self-hosted
opt-in and both existing trust stores; it does not claim that all TLS fallback
has been removed or redesign the shared server/proxy/WebSocket policy.

The original 17 native HTTP contracts remain; 10 additional private-loopback
contracts cover malformed/refused proxies, sync/async URL factories with and
without cached probes, sanitized typed errors, strict redirects/reuse and
nonstrict rejection without opt-in. `tools/native/test-http.sh` executes them
with a private HOME and temporary CA; configuration tests do not substitute for
this execution. Current-commit CI results are recorded in PR #1. Dependencies,
lockfiles, FRB signatures, protocol, app identity and permissions are unchanged.
